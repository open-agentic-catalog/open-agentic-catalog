# VS Code extension verification

The optional [extension](../../extensions/vscode/README.md) uses its own npm lock and the locally packaged TypeScript SDK. The build installer owns pinned Node 24.22.1/npm 12.2.2 under `extensions/vscode/.tools/`, independently of SDK maintainer runtimes. It leaves the user's Node selection alone.

Run these targets separately from the repository root:

```sh
make sdk-tools-install SDK_LANGUAGE=typescript
make sdk-check SDK_LANGUAGE=typescript
make sdk-package SDK_LANGUAGE=typescript
make vscode-tools-install
make vscode-check
make vscode-package
make test-vscode
```

For build/check/package only, a verified SDK archive and `make -C extensions/vscode tools-install` suffice. Local `test-tools-install` and root `vscode-tools-install` explicitly add editor fixtures; full qualification also needs the SDK maintainer installation above. Only installation acquires dependencies, VS Code or the pinned A2A sample. Checks and packaging use installed inputs; they do not publish. The pinned host is stable VS Code 1.143.1 on Linux amd64. Packaged tests need Xvfb, OpenSSL and the repository Go toolchain. Tests use owned profiles and local HTTP/TLS/issuer fixtures. They do not restart retained Compose or Minikube services.

`vscode-check` runs TypeScript, ESLint, Prettier and isolated units. Units inject editor, HTTP and secret-storage boundaries. Host identifier tests use private temporary files. Native command tests cover prompts that finish after a connection switch or sign-out, plus account verification after saved credentials are restored. They do not start servers, launch VS Code or contact a database.

Connection UI units exercise numbered native-control adapters, Back, early ID/name validation, canceled edits, fresh settings merges, same-definition conflicts, OIDC refresh inputs and fixed Settings IDs. Credential units cover delayed deletion, late writes, bounded MCP forgetting, Unicode names, safe correlation fields, actual expiry, stale callbacks and private generation checks. File-based units use owned temporary directories without launching a host.

Run `make test-tooling-unit` separately for the isolated Python launcher and package guards. This selection does not launch VS Code.

`test-vscode` first runs the actual Make/package/watch controls, then real HTTP/TLS/OIDC functional cases and activates the packaged VSIX in the selected host. It also opens the installed guide through the Help command and verifies the private host identifier. Keep their results separate.

To run application workflows while excluding Make/tooling fixtures and their cleanup tests, use the existing runner from the repository root:

```sh
python3 -B test/vscode/runner.py test --scope runtime
```

This selection builds the VSIX, runs all local HTTP/TLS/OIDC cases and qualifies the installed Linux editor. It preserves source/tool/artifact checks and owned fixture cleanup. Its separate `output/vscode/runtime-qualification.json` records `scope: runtime` and `toolingFunctional: not_selected`; it does not replace the full aggregate report. The default `--scope all` is unchanged and includes the Make/tooling fixtures. Missing prerequisites or a failed selected phase fail either selection. Only the `test` action accepts a non-default scope. Python helper units cover scope selection, separate reports, prerequisite failure, failed phases and source/artifact drift.

Browser units cover endpoint allowlists, consumed-field validation, opaque cursors, stale results, exact document integrity, numeric JSON exports and reference-only bookmarks. Session units distinguish account changes from changed permission hints, including a failed probe between valid responses. The local functional fixture covers indexed identity, partial live counts, approved artwork delivery, refusals and session invalidation after membership changes.

Session units also hold duplicate SecretStorage notification reads open during access verification. Unchanged credentials preserve the existing session guard and cancellation signal. Notifications compare the exact credential value accepted from storage or saved there; rebuilding a validated object must not manufacture a change. External credential replacement or deletion must invalidate the guard and abort pending work. These cases use explicit synchronization, without sleeps, credential retries or notification suppression. The local issuer fixture checks notifications after login and rotated-credential reloads. The installed editor also verifies OIDC credentials after native SecretStorage reselection.

`host.unit.test.mjs` also checks stale missing and older native notification reads against real private generation files. Notification reconciliation runs after queued credential writes. It retains only the accepted credential that matches the completed generation. A newer generation with an unchanged cache, real replacement/deletion, a missing generation file and corrupt generation evidence have separate assertions. A stale observation must neither erase another window's write nor cancel unchanged work. The packaged host's twelve sign-out/sign-in cycles verify both account reads and the first Catalog page without credential retries.

The local functional selection adds two real Linux editor windows sharing one owned profile and the installed VSIX. Its issuer holds verification after issuing one replacement while both windows request renewal. Exactly one refresh exchange must occur, and both windows must subsequently read with a valid login. Bounded fixture reselection checks wait only for native cache propagation, never accept `sign_in_required`, and cannot hide another refresh because the issuer counts exchanges. Private credential locks and generation hashes fence stale caches. Separate local HTTP controls cover genuine refusal, cancellation of one reader during held renewal, signed 30-second tokens without usable refresh and a signed token reaching its actual expiry. This is native profile evidence with the basic test password store, not production keyring, remote-host or OS browser-registration qualification.

The test runner creates a private `XDG_RUNTIME_DIR` with mode `0700` for editor IPC sockets. It removes that directory after the run. This avoids inherited missing or unwritable desktop paths without changing host services. Guide screenshot tests use their own directory. Failed renewal fixtures retain bounded progress reports under `output/vscode/renewal-*-failure.json`; profiles, credentials and raw native logs are excluded.

The ordinary installed-editor phase also exercises Add/Edit/Back, early duplicate-ID rejection, canceled edits, unrelated-setting preservation and safe HTTP diagnostics copied through the real clipboard. Account-status updates must preserve existing search fields. Source or VSIX Help and resource workflows retain their existing owners.

MCP units check document families, exact argument arrays, consent previews, target-secret bindings and refusal after evidence or identity changes. External-document functional checks cover redirects, size limits, outages, private CA separation and cancellation after a response starts. Cancellation must close the owned response; a subsequent valid read must succeed.

The packaged host adds four real governed kinds, scoped readers, anonymous/authenticated TLS publication, filters, facets, lazy document reads and bookmarks. Native Refresh reuses and verifies restored credentials. Its actual webview checks the message bridge, hostile text, keyboard focus, high contrast and layout. The owned editor debugging socket is loopback-only and exists only during these tests.

The same installed VSIX separately browses all six [reviewed upstream resource cases](../../internal/adapter/testdata/upstream/README.md). `upstream-host-tests.cjs` uses an owned memory Catalog and private editor connection. It checks three nonempty pages, exact release identities, native JSON/Markdown, complete Skill/Plugin inventories and all retained Plugin documents. Actual evidence buttons open the source-derived Agent Card and Unicode Skill text in native read-only editors. Package handoffs remain inert, MCP selections stay unchanged and another tenant sees no rows. The source bytes and shared fixture are hashed before and after qualification. No upstream script, package, agent or MCP endpoint is executed.

The native MCP journey starts owned HTTPS and stdio servers through **MCP: List Servers**, then invokes harmless tools through `vscode.lm.invokeTool`. Selection alone must start neither server. The HTTPS control refuses an untrusted certificate before adding the owned CA to that test process only. It never disables certificate or hostname validation or changes host trust. Target headers remain separate from Catalog tokens.

The stdio control packages a narrow owned server with the real pinned npm, installs it offline in the private workspace and starts it through native `npx`. A sentinel verifies actual startup and invocation. The child checks its Node version, its separate target credential and removal of an inherited synthetic secret. PyPI and OCI recipes also have isolated argument checks. The separate [offline runner phase](#offline-native-mcp-runners) executes actual uvx and Docker.

Modal consent and Restricted Mode run in ordinary isolated development hosts. The official extension-test runner disables workspace trust and refuses modal dialogs, so it cannot prove those boundaries. Existing browsing, Help and webview assertions retain the official test entrypoint. The native picker driver waits for rendered selection changes and only reopens a non-mutating picker after focus loss. User, extension and shared editor storage remain under the invocation directory. Both execution results and cleanup must succeed.

`vscode-package` bundles the Catalog SDK, A2A client, JOSE and transport runtime with their licenses. The local artifact is under `output/artifacts/vscode/`. The package contains no test host, tools, synthetic credentials or backend. Root `VERSION` owns its release metadata. Marketplace publication requires separate authorization.

Missing or stale installed inputs fail before tests. SDK source or release changes require a fresh SDK package and a reviewed extension lock refresh. Follow [Refresh the local SDK lock](../../documentation/src/content/docs/contributing/build-and-release.md#refresh-the-local-sdk-lock) for the executable procedure. It selects the built archive and the installed pinned Node/npm paths, then requires diff review and reinstallation. Do not bypass integrity checks. Reinstall explicitly after lock changes. Reports belong under ignored `output/`; owned profiles and fixture servers must clean up after success or failure. Each consumption workflow uses these same four targets.

`make -C extensions/vscode clean-dry-run` previews the extension-only inventory. Local `clean` removes extension dependencies, build output, tools and VSIX artifacts while preserving SDK caches, reports, developer profiles and installed resources. Root `make clean` has broader scope. Both reuse the safe preflight and refuse active extension writers. Reinstall tools explicitly after cleanup.

The package's `manifest.json` records source, SDK, runtime and tool hashes. Packaging checks its contents and excludes test code and installed development tools. These hashes identify local inputs; they are not signed artifact attestations.

Native Node coverage reports measure the handwritten core modules loaded by each scope after compilation. These include MCP interpretation, external document acquisition, package plans, archive decoding, Skill/Plugin installation/recovery and native Plugin configuration decisions. Unit and local functional reports are separate; neither includes generated SDK code, dependencies or VS Code. The VS Code entrypoint, native views and MCP/Skill/Plugin/A2A host integration have command tests and packaged host assertions outside those core percentages. The real webview renderer is exercised in the installed editor, without a separate coverage percentage.

Core coverage has separate enforced unit floors (85% lines, 80% branches, 90% functions) and local functional floors (60%, 60%, 70%). JUnit, LCOV and source/input-bound status reports live under `output/vscode/unit-coverage/` and `functional-coverage/`. Required tests, valid reports and final source checks must pass. Report admission rejects skipped/todo cases, missing selected files, duplicate or malformed coverage entries and omitted core modules. Unit and functional inventories are explicit; the local transport inventory excludes Help. Reports are staged privately; their hashes and the passing manifest are published only after validation and source checks. An incomplete attempt invalidates the previous passing marker. These are reviewed core floors, not whole-extension or native-editor coverage.

## Final desktop qualification

`test-vscode` runs the installed VSIX in five owned phases: ordinary native consumption, official host tests, an empty window, a multi-root workspace and Restricted Mode. The ordinary phase routes a local issuer callback through the editor's real `--open-url` dispatcher and registered URI handler. It uses the public `asExternalUri` mapping. It does not replace the user's operating-system URL association or open a public issuer. Browser launch and an OS default-handler registration remain outside this automated selection.

The official phase repeats twelve immediate sign-out/sign-in cycles on one actual SecretStorage key. There is no delay, retry or notification suppression between credential operations. It also verifies persisted credentials, current permissions and sign-out. The empty window permits reader browsing but refuses filesystem installation. The multi-root phase chooses the second root through the native picker, checks Git/OCI bytes and native Skill discovery, preserves the first root and removes the owned installation offline.
