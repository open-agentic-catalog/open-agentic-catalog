# Local SonarQube

Use the free, self-hosted SonarQube Community Build dashboard to review analyzer findings alongside the repository's existing checks. It is optional and report-only; it does not replace lint, security, unit, functional or coverage gates. No SonarCloud account, subscription, CI configuration or application change is required.

## Start and scan

Prerequisites: Linux AMD64, a local Unix-socket Docker engine with Compose, Python 3, Git and the locked UI dependencies installed through `make ui-install`. Allow at least 12 GiB of available container memory plus host headroom: the server is capped at 4 GiB and the scanner at 8 GiB with a 6 GiB Java heap. Other running environments need additional resources.

The image pins in [images.json](images.json) qualify Community Build 26.9.0.129388 and scanner CLI 8.1.0.6389; ARM emulation is not qualified.

Follow the reader guide to [start and scan](../../documentation/src/content/docs/contributing/testing.md#optional-local-sonarqube-dashboard), [log in and retrieve the local password](../../documentation/src/content/docs/contributing/testing.md#log-in-to-sonarqube), and [troubleshoot access](../../documentation/src/content/docs/contributing/testing.md#stop-restart-and-troubleshoot-sonarqube). The default dashboard is `http://127.0.0.1:19000/dashboard?id=open-agentic-catalog`; username `admin` uses the generated `password` field in private `output/sonarqube/credentials.json`. `make sonarqube-credentials` displays the saved URL, username and password locally, even while Sonar is stopped; keep its output out of shared logs.

The file is shared by login and scanner authentication and must be retained with the analysis data. `SONAR_PORT=19001 make sonarqube-up` selects and remembers another unprivileged loopback port.

Image acquisition is explicit. Startup and scanning use installed digest-pinned images with `--pull never`. Targets ignore the Catalog workflow env file, require a single Make goal and serialize this checkout's Docker operations.

The credentials target only reads the initialized private state and requires no Docker or network access. They reject remote Docker contexts and resources without the checkout's ownership label. They do not start, stop or modify Catalog, PostgreSQL, browser or documentation environments.

## Import existing coverage

Generate reports with their existing targets, then explicitly select the files to import:

```sh
make coverage-unit
make ui-coverage CATALOG_ENV_FILE=/dev/null
make sonarqube-scan SONAR_GO_COVERAGE=coverage/unit.out SONAR_JS_COVERAGE=output/coverage/catalog-ui/lcov.info
```

A compatible freshly generated `coverage/full.out` may replace `coverage/unit.out` when full Go functional/PostgreSQL coverage is wanted; produce it separately with `make coverage-full`. These are different test selections. Browser LCOV is a separate explicit input, not automatically combined with Vitest.

Never add their percentages.

The runner accepts the existing atomic Go profiles, deduplicates repeated blocks using the existing coverage parser (observed hits become 0/1), normalizes Go module and frontend source paths, rejects reports referring outside the selected source snapshot, and records each input's path and SHA-256. It does not independently prove that a supplied report is fresh, complete or generated by a passing test run. Regenerate against the same source and inspect the producing gate before importing.

Omitting both variables imports no coverage. Sonar's line/condition denominator includes analyzable source without imported coverage, including tooling; it differs from Go weighted statement coverage and the frontend's own report. Use the existing coverage reports for regression floors and like-for-like comparisons.

## Scope and results

Each scan applies [quality-profiles.json](quality-profiles.json) to project-specific `Open Agentic Catalog` profiles for Go, Python, JavaScript and TypeScript. These inherit `Sonar way` and override only cognitive complexity (`S3776`, maximum 40) and function parameter count (`S107`, maximum 15). Both rules remain enabled.

Security, reliability, other maintainability rules, severities, exclusions, the quality gate and server-wide default profiles are unchanged. Sonar's rule parameter names differ by language, so retain their exact spelling in the policy. Change the checked-in values rather than those eight parameters in the dashboard: the next scan restores the repository policy and verifies the values before analysis.

Reports include the selected profile keys and overrides. No separate setup target is needed.

The runner copies current tracked and nonignored untracked source into a per-run snapshot and records its digest, file count and Git commit. The commit alone does not identify uncommitted contents. It includes maintained Go, TypeScript/JavaScript, Python, CSS, shell, JSON/YAML and module inputs in the application, test, deployment and documentation roots.

Sonar decides which languages/files its installed analyzers support. The snapshot excludes hidden paths, `.env`, `.git`, ignored outputs, dependencies, vendored standards and generated Go-client code. Generated A2A bindings and UI API declarations are excluded from issue analysis; the latter and read-only locked `catalog-ui/node_modules` remain available for TypeScript resolution.

Test inclusion patterns are maintained in [sonar-project.properties](sonar-project.properties).

Each scan uses a temporary project-scoped analysis token, passes it through stdin rather than command arguments, waits for server-side processing, and revokes the token during cleanup. Sources are mounted read-only; the scanner receives no Docker socket. The runner removes its temporary scanner container and snapshot on normal success or handled failure.

Forced termination or a host crash can interrupt cleanup; inspect owned resources and revoke any remaining `catalog-scan-*` tokens in the local dashboard before resuming. The private server volumes retain analyzed source and findings.

Reports and token-redacted scanner output live in `output/sonarqube/scan-*/report.json` and `scanner.log`. A completed report records image pins, analyzer versions, source identity, imported report hashes, server analysis ID, measures, quality-gate status and cleanup. Tool, ingestion or cleanup failures return nonzero and do not qualify the run.

A completed analysis returns success even when the default quality gate reports `ERROR`: findings are for review, and the output states that distinction. Review bugs and hotspots against the actual code; counts and rule severity alone do not establish defects. Do not mass-edit code or suppress existing checks to make this optional dashboard green.

## Stop and retained state

```sh
make sonarqube-down
make sonarqube-up
```

Shutdown removes only this checkout's owned service/network and preserves the named data, extensions and log volumes plus credentials. Restart retains project analysis history. There is deliberately no destructive reset target.

Moving the checkout changes its ownership identity; do not silently adopt or delete the previous volumes.

This is a developer evaluation environment using the bundled H2 database and disabled Elasticsearch production bootstrap checks, as allowed by the [local Docker setup guidance](https://docs.sonarsource.com/sonarqube-community-build/server-installation/from-docker-image/set-up-and-start-container). It is not a production Sonar deployment. The UI binds only to loopback.

The dedicated Docker bridge is not an air gap: containers have normal outbound routing. Telemetry and update-center checks are disabled, JRE/Node provisioning is skipped, and analysis uploads target only the local server. Image acquisition contacts the configured registry; this workflow has no hosted source upload integration.

Community Build is free to run locally, but its complete analyzer bundle is not entirely OSI open source. The server/scanner have LGPL licensing and bundled analyzers include the Sonar Source-Available License; bundled runtimes retain their own licenses. See [Sonar's licensing explanation](https://www.sonarsource.com/open-source/source-available/).

These are separately acquired development tools, not shipped Catalog dependencies or a change to the application's dependency license gate.

## Harness verification

Isolated decision tests live in `test/packaging/test_unit_sonarqube.py` and run through `make test-tooling-unit`. Make/process and real loopback HTTP regressions live in `test_functional_sonarqube.py`, included by `go test -tags=functional ./test/packaging`. Neither native selection requires Sonar images. Changes to the pins, runner or Compose setup additionally require real install/start/scan/import/status/stop/restart qualification; the native tests cannot establish actual analyzer or persistence behavior. Keep measured results and limits in local reports.
