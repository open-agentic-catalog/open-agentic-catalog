# Monitoring workflow tests

These files maintain optional Compose monitoring, companion-chart packaging/lifecycle wrappers and dashboard-query checks. Provisioned assets remain authoritative under [deployments/monitoring/](../../deployments/monitoring/README.md); application metric definitions live in [internal/platform/observability/](../../internal/platform/observability).

| Files | Purpose |
| --- | --- |
| [launcher.py](launcher.py) | Validated monitoring/UI/webhook selection, Compose ownership, retained-stack lifecycle and narrowly scoped monitoring reset. Local webhooks default on without creating receivers; explicit runtime settings take precedence. Builds finish before services stop; API drains before worker during recreation. |
| [queries.py](queries.py) | Dashboard expression extraction and validation using controlled query inputs. |
| [helm.py](helm.py), [test_unit_helm.py](test_unit_helm.py) | Deterministic standalone companion-chart packaging and explicitly scoped Helm lifecycle/access commands. No cluster access is required for unit tests. |
| `test_*.py`, [launcher_functional_test.go](launcher_functional_test.go) | Launcher and query safety regressions; the Go wrapper runs the Python tests in the default suite. |

Run `go test -tags=functional ./test/monitoring -shuffle=on -count=1` for focused service-free tests. `make test-tooling-unit` runs the native Python units, including query inventory and extraction, without executing PromQL. `make test-monitoring` uses the [performance supervisor](../performance/README.md) to exercise metrics, Prometheus collection and Grafana provisioning in an owned disposable stack.

The outage test stops the fixture's Prometheus and Grafana containers and confirms that both exited. It probes the API and worker directly before the stop, while both monitoring services are down, immediately after starting them, and after fresh samples arrive from both targets. Each probe must return HTTP 200 and the expected readiness response on its first attempt. During the outage an authorized reader must still retrieve the seeded Resource. After recovery the harness verifies that the original API, worker and PostgreSQL containers kept running. The report records the probes under `monitoring.catalogReadiness`.

Once scraping resumes, Prometheus must report the exact number of successful `POST /api/v1/catalog/search` responses for the local API. The test reads the API counter after seeding, then adds the client's baseline request and its successful warm-up and measured requests. The `monitoring.searchResponses` report records the setup count, client count and collected total.

The pinned Prometheus `promtool` evaluates the actual dashboard expressions against synthetic series, including counter resets, deployment/role isolation, unavailable versus idle data, weighted retry means, local embedding admission, classified API refusals, trace-export batch failures and failed/stale replicas. It does not replace a built-dashboard browser check after Grafana image, interaction or presentation changes. Check login, Role selectors, missing observations, import to a new UID and updates to an owned UID. Preserve provisioned and unrelated dashboards during import checks.

Select `make test-monitoring MONITORING_BROWSER=on` for the additional Chromium interaction check using the installed UI Playwright/Chromium tools. It runs after all measured traffic and collector checks, in that same disposable supervisor. Browser traffic never enters a timed workload window. The dashboard uses the workload's recorded absolute observation range; a changed host wall clock refuses qualification rather than substituting a moving lookback.

The browser logs in with the private fixture password file, selects Deployment `local` and Role `api`, `worker` and `All`, and checks each role's heap query and response. The heap series itself must select the requested deployment and role. At least one returned row must pair a positive heap value with a timestamp inside the recorded observation range. It imports the shipped dashboard to a unique invocation-owned UID, adds controlled `vector(0)` and absent-series panels to that owned copy, and requires visibly distinct zero/unavailable states. A second native import overwrites only the owned UID. Exact before/after dashboard JSON proves the provisioned noneditable `catalog-overview` dashboard unchanged. The browser deletes its own copy and closes its ephemeral context; the supervisor still owns stack cleanup.

Browser exceptions, unexpected console errors, HTTP failures and failed requests refuse completion. Grafana's exact new-owned-UID 404 availability lookups are recorded separately; those expected import checks do not conceal other missing assets or data-source failures. No password, browser storage or authenticated trace is retained. The selection stays optional and requires no change to application readiness.

After the healthy journey, separate owned pages calibrate refusal of a changed Role accessible name, blocked query transport and blocked built assets. Each must fail its intended visible-control/data assertion, with the actual intercepted query/asset request observed. These deliberate faults are reported as controls, separately from clean-page diagnostics, and never affect the provisioned dashboard or measured workload.

The [performance and monitoring guide](../../documentation/src/content/docs/guides/performance-and-monitoring.md) owns live commands, interpretation and safe cleanup. Its [Grafana walkthrough](../../documentation/src/content/docs/guides/performance-and-monitoring.md#read-the-grafana-dashboard) explains navigation and panels. The [screenshot procedure](../../documentation/assets/monitoring/README.md) uses a separate temporary project; this test target always cleans up its own stack. Preserve unavailable-versus-zero semantics and installation/role scoping. Do not replace missing series with unconditional zero, duplicate dashboard expressions as a second authority, contact another project's monitoring or delete PostgreSQL during monitoring-only reset.
