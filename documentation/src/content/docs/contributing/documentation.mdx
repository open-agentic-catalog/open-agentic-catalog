The reader manual and its Starlight project live in `documentation/`. Edit ordinary pages in `documentation/src/content/docs/`.

The documentation Node/npm toolchain builds only the manual. Backend Go builds and images do not depend on it. The optional UI image builds and packages the manual in a separate stage. Ordinary Go and frontend tests need no manual build. Serve the built documentation as static files; it needs no Node server.

## Install, build and preview locally

Use Node 22.23.4, pinned in `documentation/.nvmrc`, with npm 12.2.1. The supported range is Node 22.23.4+ within major 22, matching Astro's minimum.

If you use nvm, run `nvm install` inside `documentation/`. Run `nvm use` in the same directory. Otherwise, select that Node version through your usual tooling. Return to the repository root:

```sh
make docs-install
```

`docs-install` runs locked `npm ci` and can access the npm registry. `docs-build` uses installed local packages and repository inputs. It does not install tools or fetch remote schemas. Missing dependencies fail the command; run the install target explicitly.

Choose one hosting path below for an independent preview. Build and preview with the same non-secret `DOCS_BASE`. Stop your previous preview with Ctrl-C before rebuilding or changing the base. Preview serves existing output; it does not rebuild when you select a tab or edit a source.

Valid bases are `/` or slash-delimited alphanumeric, hyphen and underscore segments. The build uses no hardcoded GitHub Pages domain or repository path. It rebuilds root-relative assets and local Pagefind search for the selected base.

This repository does not configure publication to a separate documentation website. The optional UI image serves the bundled manual at `/docs/`. Analytics and versioned archives are not configured.

## Export the complete manual to PDF

Install the documentation packages and their matching headless browser explicitly:

```sh
make docs-install
make docs-pdf-browser-install
```

The second command downloads Chromium Headless Shell into `.tools/documentation-pdf/`. It requires the browser's operating-system libraries. It does not install system packages.

Build the manual, then export it:

```sh
make docs-build
make docs-pdf
```

The PDF is `output/documentation-pdf/catalog-manual.pdf`. Export reads the completed `documentation/dist/` build without changing it. It supports the build's root or non-root base. It needs no UI installation, Catalog process, database or identity provider. After package and browser acquisition, rendering uses only local inputs.

The exporter follows sidebar order and checks coverage against the content map and OpenAPI operations. It includes generated API pages, all tab alternatives and collapsed content. Code prints as wrapped monospaced text. Contents, bookmarks and cross-page links identify the combined chapters. Download references identify files in the HTML manual; the PDF does not embed downloadable contracts or archives.

Export uses a private loopback asset server and an owned browser. Navigation has a two-minute limit. Printing has a ten-minute limit; the overall export limit is fifteen minutes. Press Ctrl-C to cancel. Failure or cancellation preserves the previous PDF and closes the owned server and browser. Correct the reported problem, rebuild changed inputs, then run the export again.

Each successful render writes a separate JSON report beside the PDF. It records input and output hashes, chapter routes, tool versions, browser identity and cleanup. A report establishes successful rendering, not visual qualification. Inspect the PDF after changing print layout, content components or the renderer. PDF bytes can differ between runs and operating systems.

The PDF includes the built manual's license and third-party notices. Playwright and its core package use Apache License 2.0. Browser binaries and installed fonts have separate terms. Keep their notices with any redistributed tools or fonts. Browser executables remain local tools; they do not enter the site or application images. The current export is qualified on Linux with the pinned headless browser. Font substitution can change pagination. Chromium creates structure tags for the bookmarks. These tags do not establish PDF accessibility compliance.

Ordinary site builds and checks do not install or launch this browser. Run `make test-docs-pdf` explicitly for real PDF regression tests. It also requires `pdftotext`, `pdfinfo` and `mutool`. Pure transformation tests run with the normal documentation units. Exports and reports remain ignored local artifacts. External publication remains maintainer-owned.

`make clean` removes the PDF browser cache and default export directory. `make clean-output` removes the default export directory without removing the browser. Stop exports before cleanup.

## Prepare the public website and PDF

The selected public address is `https://open-agentic-catalog.github.io/open-agentic-catalog/`. Ordinary builds and the UI's `/docs/` manual keep their existing bases.

Install documentation packages and the PDF browser as described above. Run source and site checks before the final build:

```sh
make docs-check
make docs-site-check
export DOCS_SITE=https://open-agentic-catalog.github.io
export DOCS_BASE=/open-agentic-catalog/
export DOCS_EDITION_COMMIT="$(git rev-parse HEAD)"
export DOCS_DELIVERY_OUTPUT=output/documentation-delivery/review-1
make docs-build
make docs-delivery
```

Select a new output directory for each preparation. The homepage displays the application version, full source revision and PDF download. Delivery copies the sealed build and its matching PDF into the selected directory. A separate `documentation-delivery.json` inventories the final tree. The original bundle stays unchanged. Ordinary files retain their 32 MiB limit; only the complete PDF permits up to 128 MiB. Total delivery permits 384 MiB.

Preparation uses local files after tool acquisition. It does not upload or publish. It verifies the PDF against the exported build and checks the selected website address and base. Changed inputs require a new build and export. Failure prevents an incomplete edition from replacing a delivered edition. Correct the failure and prepare a new directory.

The maintainer enables GitHub Pages with the Actions source and restricts the `github-pages` environment to `main`. The Pages workflow prepares editions on `main` and manual dispatch. Deployment requires `deploy=true`, or `PAGES_ENABLED=true` for a push to `main`. Pull requests cannot deploy. Only the separate deployment job receives Pages and identity-token permissions. Hosted delivery requires maintainer verification; local preparation does not prove GitHub settings.

`make clean-output` removes these delivery directories. Stop active builds and exports before cleanup.

## How the manual is built

`make docs-build` runs these steps through the documentation project's locked npm scripts:

1. Validate the content map and prepare registered reference pages, exact downloads, dependency inventories and license notices.
2. Render the pages with Astro, Starlight and the local OpenAPI contract. Create the local Pagefind search index.
3. Write `documentation-bundle.json` from the final output. Record the hosting base, each file's size and SHA-256, and exact inline script and style hashes.

The output is `documentation/dist/`. Do not edit generated pages or the bundle manifest. Edit the owning source and rebuild. The [source ownership table](#one-editable-source-per-topic) identifies those sources.

The manual contains registered reader pages and explicitly selected public downloads. Task trackers, engineering records, runtime credentials and browser sessions are not build inputs. A standalone static host needs only `documentation/dist/`; it needs no Catalog API or Node runtime.

## Read the manual through the UI

The UI image packages the manual automatically. Open **Help > Documentation** to read it at `/docs/`. This route stays at the origin root when the UI uses another base path. The manual is public and does not require sign-in.

### Packaged UI

`catalog-ui/Containerfile` installs the locked documentation packages in a separate build stage. It renders the manual with network access disabled and `DOCS_BASE=/docs/`. The final image includes static output and license notices, without Node, npm or an Astro server. Backend images remain independent.

Build and inspect the UI image from the repository root:

```sh
make ui-container-build
make ui-container-inspect
```

These commands do not replace a running container. Follow the existing [Compose or Helm deployment procedure](../operations/maintenance.mdx#coordinated-release-deployment) to run the new image. Rebuild and redeploy after documentation changes; `make docs-build` alone does not update a running UI image.

Image inspection checks every file and the notices against the selected image's bundle manifest. See [UI image delivery](./build-and-release.md#optional-ui-image) for caching, browser security policy, inventories and verification targets.

### Source development

Install the separate UI and documentation packages with `make ui-install` and `make docs-install`. Start the [local API](../guides/local-development.mdx#start-the-service) before the UI. Stop an existing UI on port 4180 before this launch:

```sh
make docs-build DOCS_BASE=/docs/
make ui-dev UI_DOCUMENTATION_DIRECTORY="$PWD/documentation/dist"
```

`ui-dev` builds the React assets and Go host. The launcher checks and copies the prepared manual into temporary UI assets. It leaves `documentation/dist/` unchanged and removes its temporary files when it stops. Rebuild the manual and restart `ui-dev` after documentation changes.

Without a prepared manual or explicit URL, ordinary source runs omit the Documentation link. Ordinary source tests do not require a manual build. For a separately hosted site, use the optional [HTTPS documentation override](../reference/configuration.mdx#ui-documentation).

Use MDX comments instead of HTML comments when a comment is necessary. Remove obsolete Markdown lint comments after conversion, and register new component names in the Markdown lint allowlist. Preserve explicit anchor elements and every code example.

The shared stylesheet supports light and dark themes and horizontal scrolling within diagrams on narrow screens. Check all diagrams after changing shared styles.

Use the existing SVG components and shared architecture styles for flows, state transitions and relationships. Use native FileTree for a small package layout. Do not draw diagrams or directory maps with ASCII characters in code blocks. Keep commands, configuration and response examples as copyable code.

The [Starlight code renderer](https://starlight.astro.build/reference/configuration/#expressivecode) preserves shell comments when readers copy examples. Keep `expressiveCode.frames.removeCommentsWhenCopyingTerminalFrames` set to `false` in the site configuration. Removing comment lines can also remove required file content inside a heredoc. Check the clipboard text after changing a code block or its presentation.

A projected Markdown source can use a `<!-- diagram: ComponentName -->` marker with that component listed in its content-map `diagrams` array. The build creates an MDX projection with the matching import, requires each marker exactly once and rejects unregistered markers. Keep explanatory prose beside the marker in the source. The component owns the drawing; do not maintain an ASCII copy of it.

Use real UI screenshots beside the workflow they illustrate, with descriptive alt text, a short caption and a link to the full-size image.

Capture synthetic demo data using a test identity; exclude credentials, session cookies and private customer data. Keep raw browser evidence in ignored `output/playwright/`. Copy reviewed Catalog UI images into `documentation/assets/catalog-ui/` and monitoring images into `documentation/assets/monitoring/`. Keep a repeatable capture procedure in each asset directory's README.

Register those images in the `downloads` allowlist in `scripts/site.mjs`; relative Markdown image links then work at both root and non-root site bases.

Refresh screenshots when the pictured controls or workflow change, and check the rendered page at desktop and mobile widths. Keep instructions in text so screenshots are not the only way to follow a procedure.

Keep Markdown ASCII with one-line paragraphs and one frontmatter `title`, without a duplicate H1. Write ordinary relative links that work from the source file in the repository. The build maps included pages to local site routes. References to code outside the site retain their text without inventing a public repository URL.

Reader procedures must link to published guides or include the necessary instructions; do not send readers to internal trackers or test records. No edit link is configured until a real publication/repository destination is selected.

## Writing style

Write for someone using, operating or contributing to the project. State what the software does and what the reader needs to do, not who requested a change or how a work session unfolded.

These rules apply to usage, contribution, architecture, development, testing, deployment and operations documentation, including records and trackers. The published manual serves users, developers, architects and operators. Site inclusion determines publication location, not audience or writing standards. Keep useful evidence and chronology in records, but remove conversational history and repetitive session recaps from them too.

### Use Simplified Technical English

Apply [ASD-STE100 Simplified Technical English](https://asd-ste100.org/) principles where practical. The rules below adapt those principles to software documentation. They do not establish full compliance with the standard's controlled dictionary and writing rules.

- Aim for 20 words or fewer in an instruction and 25 in a descriptive sentence. Split a long sentence at a logical boundary.
- Give one instruction in each sentence. Start a procedural step with a verb. State a prerequisite before the action that needs it.
- Prefer active voice. Identify who performs an action when responsibility matters. Use simple present, past or future tense where possible.
- Retain articles such as "a" and "the". Do not omit words that the reader needs to understand a condition or action.
- Use a simple verb instead of an unnecessary "-ing" construction. Keep established technical terms, such as "listing", "tracing" and "connection pooling".
- Use the same name for the same concept. Use each term with a consistent meaning. Explain necessary technical terms and acronyms at first use.
- Avoid noun chains longer than three words. Use a phrase such as "configuration for the API listener" when a noun chain is unclear.
- Write "do not" for a prohibition. Preserve exact field names, commands, media types, product names and normative terms such as MUST and SHOULD.
- Keep each paragraph to one topic and six sentences or fewer. Use lists or tables when they make choices, conditions or steps clearer.

Treat sentence lengths as review targets, not an automatic gate. Code, URLs, tables and exact technical names need separate judgment. Do not change a requirement or remove a useful condition to meet a word count.

### Remove unnecessary words

- Remove words and sentences that add no information. Keep prerequisites, limits, failure consequences and security requirements.
- Remove remarks about the text, such as "as you can see", "this is important" or "this is the interesting part".
- Replace abstract language with the concrete behavior. For example, write "Clients use ARD to find resources" instead of "ARD provides a discovery projection".
- Explain the relevant limitation once, beside the behavior it affects. Link to details instead of repeating broad exclusions.
- Preserve uncertainty. Do not change "the test did not reproduce the failure" into "the failure cannot occur".

### Document behavior, not work history

- Use present tense for current behavior and imperative steps for procedures. Describe planned features as unavailable or deferred; do not imply that a design is implemented.
- Use descriptive headings such as "Run container tests" or "Known limitations", not "Scope clarification", "Completion recheck" or dated documentation-update headings.
- Keep conversation history, approval narratives and routine edit journals out of project documents. Git history records ordinary edits.
- Name a role only when it matters to the instruction: for example, a Tenant Administrator approves a publication domain and the database schema owner runs migrations. Avoid vague attribution such as "the owner confirmed" or "as requested".
- Keep backlog IDs and work sequencing in the tracker and handoff. Reader pages explain capabilities, requirements and procedures without requiring knowledge of the backlog.
- Use topic names for links, such as "Database roles", not filenames such as "database-roles.mdx". Mention filenames when the reader needs to edit, run or validate that file, or when the name is part of a format such as `SKILL.md`.
- Link standard, tool and reference implementation names where readers need more detail, including names in tables. Prefer official specifications, project documentation or source repositories. Put the link at the relevant name, not only in a source list. Use versioned specifications or pinned sources for exact version claims. Check destinations and redirects. Avoid repeated links that distract from the text.
- Keep source-location notices and generated-page editing instructions out of reader pages. Explain where contributors edit documentation in this guide, not in a banner on every reference page. Implementation status stays in the repository-only tracking directory and is excluded from site navigation, generated pages and search.
- Give each topic one maintained source. Link to details instead of repeating implementation summaries, run histories or long lists of exclusions.
- Preserve concrete limits, prerequisites, security warnings and unresolved defects. Replace general disclaimers with the specific limitation relevant to the task.
- Omit obvious disclaimers such as "this repository is not a SaaS" or "the chart is not a production environment". State the actionable requirement instead: supply PostgreSQL, configure an issuer or inject the required credentials.
- Use dates for test measurements, security scans and releases when chronology matters. Ordinary reference and how-to text does not need a date or a "now implemented" narrative.
- Test records identify the build, environment, command, result and relevant limitation. Separate observations from suspected causes; a later passing run does not explain an earlier failure.
- Keep dated source comparisons and test results in engineering records. Explain supported behavior and compatibility limits in reader pages. Dates in specification titles identify versions, not editing sessions.
- Separate specification requirements, Catalog rules and observed client behavior. Link to primary specifications for requirements and pinned profiles for implemented versions. Announcements do not define conformance.
- ADRs describe current decisions, rationale, alternatives, consequences and limits. Update the owning ADR in place and preserve its identifier and route. Keep amendment journals, supersession chains, obsolete backlog IDs and implementation histories out of ADRs. Git retains edit history. Released API and stored-data compatibility obligations still apply.
- Apply this style to HTML, diagrams, API descriptions, configuration comments, command help and code comments as well as Markdown. Comments explain behavior or rationale, not the editing session. Preserve protocol names, technical ownership terms, third-party text, generated bindings and immutable migrations.

For example, replace "The owner approved the new testing approach" with "Run the applicable tests against each build." Replace "The latest follow-up now completes the webhook slice" with "Webhooks are disabled by default and deliver signed HTTPS notifications when enabled."

After a rewrite, compare the text with its authoritative source. Confirm that conditions, permissions, required actions and failure consequences retain their meaning. Read the page without relying on the conversation, backlog or previous work sessions.

## Verify a documentation change

```sh
make check
make docs-site-check
```

The separate `lint` command checks maintained `.mjs` tooling, configuration and tests, including new files. It uses installed ESLint 10.13.0, `@eslint/js` 10.0.1 and globals 17.13.0. Recommended correctness rules use Node ES-module globals; they do not format files or check Astro/TypeScript. The command uses explicit configuration and disables inline overrides, caching and fixes.
