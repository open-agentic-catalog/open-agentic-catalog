# Post-code verification

Work from the repository root. Resolve instruction paths from that root. Use `AGENTS.md#test-and-verification-workflow`, the testing guide (`documentation/src/content/docs/contributing/testing.md`), and the current `Makefile` as the verification authority. Inspect the owning harness README and npm scripts when selecting frontend, documentation or tooling checks. Reuse maintained gates; this skill adds no test runner, dependency installer or Make target.

For independent SDK changes, follow the SDK harness (`test/sdk/README.md`). `make sdk-check` checks all languages by default; `SDK_LANGUAGE=go|python|typescript|rust` narrows selection. Root application tests exclude the nested SDKs. Keep SDK units, local HTTP/TLS and outside-checkout package consumers distinct. `sdk-package` builds local artifacts without tests or publication. Version bumps update derived Python/npm/Cargo metadata; regenerate and requalify after a bump.

For the optional VS Code client, follow the extension harness (`test/vscode/README.md`). Run `vscode-check` for types, lint and isolated units. Run `test-vscode` for local HTTP/TLS/OIDC and installed-VSIX host tests; it also packages the current extension. `vscode-package` builds without tests. Run these goals separately and sequentially because they share build outputs. Explicit local `tools-install` acquires build dependencies; `test-tools-install` or root `vscode-tools-install` also acquires editor fixtures. SDK changes also require the affected SDK checks and a current local package/extension lock. Root application gates do not qualify the extension. Keep unit and functional coverage separate; real-host assertions have no coverage percentage.

## Review the change and select its checks

Inspect `git status --short`, staged and unstaged diffs, and relevant new files. Review implementation against its owning contract, including failure paths, callers, permissions and affected build variants. Check for lost assertions, changed test selection, weakened coverage floors and unintended generated files or snapshot changes. Test counts alone do not establish assertion preservation. Use unit-testing (`.agents/skills/unit-testing/SKILL.md`) or functional-testing (`.agents/skills/functional-testing/SKILL.md`) when adding or repairing tests.

Review assertion quality as well as pass/fail results: check that expectations come from the contract, negative cases reach the intended guard, and relevant state changes or side effects are observed. Apply the failure investigation rules (`documentation/src/content/docs/contributing/testing.md#writing-tests`); report confirmed product bugs separately from test/tooling repairs and mutation catches. A clean run establishes only the exercised scope.

For logging/error-boundary changes, capture the actual affected stdout/stderr, HTTP fallback or trace output with synthetic secret and panic sentinels plus successful controls. Verify severity, configured filtering/format where implemented, single diagnostic ownership, failure/cancellation and unchanged required audit/replay behavior. Formatter escaping alone is not a no-leak assertion, and a returned error alone does not verify what a compiled command prints. Keep subprocess/listener probes functional and use the owning fixtures; ADR-0021 (`documentation/src/content/docs/architecture/decisions/0021-logging-observability-and-audit.md`) defines backend/UI event ownership and retained runtime/collection limits. Verify the final response classification and persisted Job result, not an intermediate error or deferred callback alone; actual local spans own sampling fields, and filtered/suppressed diagnostics must leave counters complete.

An explicit unit-only request limits test execution to the relevant isolated selections in the unit-testing skill; report broader functional verification as unrun. Select requested lint/analysis separately and avoid aggregates that add functional tests. Units must not start listeners, use real network/DNS, spawn fixture subprocesses, run application binaries, or access databases/browsers/providers. Normal test compilation and runner workers are allowed; composed application workflows remain functional even with memory stores. `make test`, `make verify` and `make test-ui` include functional tests and are not unit-only substitutes.

For normal post-code verification, select the applicable rows and boundary-specific additions required by AGENTS.md:

| Changed scope | Verification |
| --- | --- |
| Go, including the UI host | Format changed Go files and run focused affected tests with their correct build tags. Run `make test-unit` separately, or `make coverage-unit` when unit coverage is needed, then `make check verify`. Add the affected real-boundary gates below. |
| UI client, authentication host or Node tooling | Run `make test-ui`, which includes `ui-check`, `ui-test`, an isolated build and browser journeys. During iteration, use the focused checks or `make ui-test-unit` as appropriate. A UI Go host change follows both this row and the Go row. |
| Python or other Node tooling | Run the existing native units and relevant functional harness from the owning README, plus `make check` and applicable npm checks. Process/Make/CLI fixtures stay functional; a Go wrapper does not make a Python suite isolated. |
| Documentation, trackers or skills | Run `make check`, which includes `docs-check`. Add `make docs-site-check` for reader-site content or tooling changes. Skills and tracker prose alone do not require application/browser regression runs. |

For API, SQL/migration/RLS, parser/security, standards, images or deployment changes, use the additional-gate matrix (`AGENTS.md#test-and-verification-workflow`) and the owning runbook. Real database assertions require `test-integration` or the applicable instrumented PostgreSQL gate; fake transactions and tagged compilation do not qualify SQL behavior. Packaged API journeys use `test-functional`; UI packaging/login uses `test-ui-compose` and `test-ui-oidc`.

Appearance or frontend dependency changes need `ui-visual`. Dependency changes also need local `ui-deps-check` and the affected packaging gates in UI dependency maintenance (`documentation/src/content/docs/reference/dependencies.md#ui-dependency-maintenance`). `ui-deps-audit` submits dependency metadata to its registry; external registry audits are maintainer-only. Leave them unrun and report that limit.

Select cluster, model, interoperability or performance fixtures only for a relevant changed boundary or requested scope, preserving their documented prerequisites and explicit-scope requirements. A related code change alone does not authorize arbitrary external peer execution or hosted calls.

## Avoid duplicate and misleading checks

- `check` covers Go formatting/vet/Staticcheck/golangci-lint, shell, Markdown, JSON/YAML, container/Compose source, API and Python/Ruff checks. `verify` adds broad local Go functional/race/coverage tests, profiles, conformance fixtures and binary checks. Neither runs frontend/browser tests, a real database, deployed stacks or the built documentation site. Service-free does not mean unit-only or offline.
- Use `make check verify` in one normal invocation to share prerequisites such as `lint` and `dead-code-check`. Do not combine isolated goals such as `test-unit`, `coverage-unit`, `test-tooling-unit` or `ui-test-unit` with other Make goals; they deliberately bypass workflow env files and require separate invocations.
- Changes to the UI performance collector, budgets or measured behavior require the separate `make ui-performance` and its accounting/configuration/functional calibrations. Use the performance skill for cold/warm identity, report-only timing and adjustable execution deadlines. Ordinary `test-ui` and instrumented browser coverage exclude this selection.
- `test-ui` already runs ESLint/Prettier, TypeScript, generated API drift, frontend coverage, Node unit/functional tests and Go host tests. Do not precede a final `test-ui` run with the same complete `ui-check`, `ui-test` and `ui-coverage` suites unless an earlier failure or subsequent edit warrants it.
- `coverage-unit` executes the complete isolated Go selection; do not repeat `test-unit` solely to obtain the same result. Keep constituent coverage reports and denominators explicit; use the maintained combined Go target below when that scope is requested. `ui-coverage-100` is an opt-in exact-target diagnostic, not the maintained frontend regression floor.

## Measure and report the requested coverage

Follow coverage accounting (`documentation/src/content/docs/contributing/testing.md#coverage-accounting`). Select the execution boundary before quoting a percentage:

| Requested scope | Existing gate and evidence |
| --- | --- |
| Isolated Go units | `make coverage-unit`, alone; `coverage/unit.out` and weighted application package/file summaries, including the UI Go host and zero-hit database code. |
| Units plus local functional tests | `make coverage-check coverage-core-check`; `coverage/default.out` and its database-source-excluding `coverage/core.out`. Core is a filtered local profile, not a pure-unit selection. |
| Real PostgreSQL repository coverage | `make coverage-postgres-check`; `coverage/postgres.out` has the database-package denominator. |
| Real CLI/API/worker process coverage with PostgreSQL | `make coverage-process-postgres-profile`; `coverage/process-postgres.out` supplements repository tests. It instruments the assertions also run by `test-process-postgres`. |
| Full combined Go application coverage | `make coverage-full`, alone; fresh unit/local/PostgreSQL/process profiles, `coverage/full.out` and separate totals plus the lowest-first file report in `coverage/full.txt`. |

Full coverage runs its constituent gates sequentially and enforces their separate aggregate/critical-package floors plus the combined aggregate and application per-file floors. Use the exact statement-count comparisons in the existing helpers; rounded percentages cannot decide a pass. The shared critical-package list applies independently to unit and local profiles, without a per-file unit requirement.

Do not pre-run those suites merely to regenerate them again, run concurrent profile writers or select full/process/PostgreSQL execution under a unit-only limit. Other applicable source, race, standards and workflow checks remain required; combined coverage does not replace them.

For reports, state the suite, source/run identity, included roots and covered/total statements. Reuse the maintained accounting helpers (`test/packaging/README.md`) and their complete inventory. Calculate totals from unique weighted blocks; combine compatible Go profiles by whether any suite hit a block, never by adding percentages or overlapping totals. Normalize broad local coverage to the application inventory when comparing it with unit/full application coverage. Keep backend-only and UI-inclusive results labelled.

For lowest-file lists, sort exact covered/total ratios with a path tie-break and show the percentage and uncovered statements. Retain zero-hit application files; files without executable statements are not zero-covered. Unit file summaries are ordered by path, whereas the combined report is already ordered by coverage. `go tool cover -func` lists functions, not a per-file ranking. A zero means no hit in the named suite, not necessarily no tests, and statement coverage does not establish branch or workflow completeness.

Make summary/check/HTML targets can rerun tests through profile prerequisites. To inspect existing evidence, use the existing profiles/reports or Go's own cover tool without invoking a regenerating target. Establish freshness before merging or calling a result current: `coverage-full` checks source identity across its run and rejects incompatible/incomplete inputs. A failed gate can leave the last successful profile on disk; report the failure and label that older result accurately.

Frontend `make ui-coverage` has a separate JavaScript denominator. Browser-driven `make ui-coverage-e2e UI_E2E_PROFILE=local|compose|oidc|semantic` uses separately qualified private Istanbul builds and complete document/context capture. Check execution and cleanup status before interpreting its unique per-run reports; keep each profile separate from Vitest, Go and operation coverage. Its instrumented packaged runs supplement ordinary image/browser gates.

`make functional-coverage FUNCTIONAL_REPORTS='...'` reads explicitly selected compatible packaged reports and measures API-operation obligations; it does not run services or measure Go statements. Neither joins the Go percentage. Retain dated measurements and meaningful gaps in the owning record instead of copying coverage numbers into skill instructions.

## Check dead code without weakening behavior

The Go `dead-code-check` already runs through `lint`, `check` and `verify`, including the UI Go host. Use `make dead-code-report` to investigate findings; report mode tolerates reviewed or unreviewed findings but still fails on tool/discovery/report errors. After a successful aggregate, repeat its dead-code scan only for a change or unresolved finding. Read unreachable-function analysis (`documentation/src/content/docs/contributing/testing.md#unreachable-function-analysis`) for the production and test scopes, exception policy and tool acquisition.

Before removing a finding, inspect actual callers, tests, interface/reflection uses and build variants. Preserve useful test support and contract inventories. Uncovered statements and production-unreachable helpers are not automatic deletion instructions. Do not accept broad exclusions or manufacture callers to silence a finding. After removal, reconcile assertions and coverage denominators, rerun the affected tests and scans, and retain exact reasons for legitimate exceptions.

Frontend `ui-dead-code-report` and `ui-dead-code-check` use the locally installed pinned Knip with full application/test/tooling and production-browser scopes.

The check runs once through `ui-check` and `test-ui`; backend checks and isolated unit targets stay independent. Install through `ui-install`, never a global fallback or `npx` acquisition. Report mode tolerates findings but still fails on tool/configuration errors. Review both scopes, actual consumers and narrow generated/framework exceptions under UI dead-code analysis (`documentation/src/content/docs/contributing/testing.md#ui-dead-code-analysis`).

After a pin/configuration change, run the actual-tool functional fixtures and the affected dependency/image gates; preserve Playwright guards and never automatically remove findings. Static reachability does not replace CSS/layout or browser verification.

## Run, repair and hand off

Use repository-pinned tools and explicit installed prerequisites; consult the owning installation instructions if a tool is missing. For Ruff, set `RUFF` to the installed executable matching `ruff.toml` when PATH differs. Do not silently install a latest analyzer, change a version pin, disable checks or call an incomplete gate passed. Normal Make goals may load the selected workflow env file; use `CATALOG_ENV_FILE=/dev/null` when verification should omit those local settings.

Keep tracked files, including documentation, and non-ignored inputs unchanged while source-bound coverage, mutation or packaged supervisors are running; update result records and trackers after they finish. Keep fixture ownership and cleanup intact. Run browser gates sequentially and avoid concurrent Compose/Minikube network changes; finish documentation builds before filesystem security scans. Preserve retained services and data. Never regenerate expected screenshots, lower coverage floors, skip assertions or widen dead-code exceptions solely to make verification pass.

Inspect failures, fix demonstrated defects within scope, then rerun the affected checks. Repeat broader gates when the fix changes their tested inputs or leaves an unresolved concern. Preserve evidence of intermittent failures and missing prerequisites; a later pass does not explain their cause. Report any required unrun or blocked scope accurately.

Finish with `git diff --check` and a final source/fixture review. Record commands, results, meaningful skips, cleanup and remaining limits; keep raw logs and generated reports under ignored `output/`. Reviewed measurements may use the optional private records described in `AGENTS.md`. Keep unresolved actionable findings in the owning tracker. Update tracker/handoff state when the work changes it, closing only completed scope. Stage or commit only when explicitly requested. External distribution and uploads remain maintainer-only; verification does not authorize them.

For relevant changes in the reviewed mutation scopes, run `make test-mutation MUTATION_PACKAGE=...` separately and inspect its fresh report using mutation assessment (`documentation/src/content/docs/contributing/testing.md#mutation-testing-and-assertion-strength`). It is not an aggregate prerequisite or statement-coverage measure. Runner/tool changes require native helper tests and the packaging guide's actual-tool qualification; reject failed baselines, infrastructure errors and incomplete evidence before interpreting survivors.

After changing behavior covered by maintained properties, their assertions or their generators, run `make test-property` alone with recorded seeds alongside the complete owning suite. Property/runner changes use the structured property gates (`documentation/src/content/docs/contributing/testing.md#structured-go-properties`), including explicit real-tool qualification for runner or pin updates; reject incomplete counts and ignored replay evidence.

For changes to Job retry arithmetic, its caller binding or formal tooling, run the explicit formal gate (`test/formal/README.md`): `make test-formal` alone with installed tools. Require a complete current-source proof and all diagnostic/calibration outcomes; reject missing or contradictory contracts, drift, parser/tool failures and incomplete results. Install only through the separate `formal-tools-install` target. Ordinary tests and coverage remain required; formal success proves only the documented scalar obligations.

Run `make test-api-generated` after changes to its harness or selected API boundaries, with explicitly installed tools. These include Namespace operations, Search/browse, Resource/Version lists and Resource/Version creation. Follow the generated API guide (`test/apigenerated/README.md`): preserve unchanged OpenAPI input, successful controls, serialization-aware negatives, strict error/state assertions, native report completeness, bounded owned fixtures and cleanup. Requalify actual-tool calibrations when changing the pin or runner. Record genuine defects separately from generator limitations; ordinary unit tests must not acquire or execute Schemathesis.

Changes to ZAP tooling, selected search/browse behavior or the observed UI session/reader boundary require the applicable explicit `test-security-passive`/`test-security-active` gates following the security harness (`test/security/README.md`). Inspect calibrations, observed routes, completed rules, findings and cleanup; an empty report or tool exit alone is insufficient. Keep this scoped scanner evidence separate from Go coverage and curated functional assertions.

Combine only successful compatible run directories with `make ui-coverage-e2e-report UI_E2E_REPORTS='...'`. Review its explicit profile list, weighted union, `files.txt` and `gaps.json`; a subset is not all-profile qualification. The semantic selection reuses the full owned MiniLM supervisor, including 1,000-release qualification, and requires its pinned offline prerequisites. It supplements ordinary `test-semantic`. Keep public rebuilds before outage continuation capture and wait for accepted Jobs; preserve exact provider-outage versus stale-cursor expectations.

For changes within the selected frontend property or mutation scope, run each applicable gate: `ui-test-property` and `ui-test-mutation`. Follow the frontend inventory (`catalog-ui/tests/assertion-strength.md`). Keep source inputs stable while measuring; review incomplete execution and every survivor. Generated namespace sequences remain under `test-api-generated`, with exact response and state assertions. For benchmark tooling, run native tests, actual-tool controls and serial matched `bench`/`bench-compare` runs; do not infer performance from tests run under unrelated concurrent workloads.

For local image or scanner changes, use `container-inspect`/`ui-container-inspect`, `sbom`/`ui-sbom` and `container-scan`/`ui-container-scan` with the exact build version, commit and platform. Follow the artifact scan procedure (`documentation/src/content/docs/contributing/build-and-release.md#scan-local-images`) for the qualified Trivy pin, explicit database acquisition and private evidence. Require complete native inventories and distinguish findings from tool failures; a missing/stale database or absent report is not a clean scan. Requalify actual positive controls and both architectures after scanner changes. Static ARM64 analysis does not qualify ARM64 execution.

Build/version metadata or its tooling changes require `make version-check` and disposable Git/actual-tool qualification described in the testing guide (`documentation/src/content/docs/contributing/testing.md#build-identity-tooling-tests`). Select `CATALOG_TEST_UV` explicitly to execute installer qualification; skipped actual-tool cases are not passes. Ordinary checks must never acquire tools or create release tags.

For Rust, run `make sdk-check SDK_LANGUAGE=rust` after explicit installation. It includes both compiler versions, isolated units, compiled examples, owned HTTP/TLS and extracted-crate consumers. Native LLVM reports handwritten unit and combined local functional coverage separately. Cargo-deny is not a prerequisite for generation, builds, tests or packaging. Use the separate `make sdk-rust-audit-tools-install` and `make sdk-rust-audit` targets for license and advisory audits. Report their result separately; a normal SDK pass does not imply an audit pass. See the harness for the audit procedure and generator-only informational exception.
